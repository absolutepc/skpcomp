# SKP: резервный Passkey владельца на основном сайте

Дата: 6 ноября 2026. Работа только в `feature/vercel-admin-qr-passkeys`, Draft PR #28.
Это подготовка к внедрению, а не разрешение на изменение рабочей БД или deployment.
Отдельный staging-проект не требуется и не создавался. Парольный вход сохраняется.

## Реализованный production-режим

`SKP_ADMIN_OWNER_BACKUP_ENROLLMENT=production` — новый **явный opt-in**, по умолчанию выключен. Принимается только PostgreSQL, `NODE_ENV=production`, `VERCEL_ENV=production` и точное совпадение request URL/Origin с `https://skpcomp.vercel.app`. Старое значение `staging` не открывает доступ на основном домене. Переменные окружения рабочего сайта не изменялись.

- Управлять ключами может только действующий owner с индивидуальной серверной сессией. Общий пароль не даёт права добавлять ключи owner.
- Перед добавлением/отзывом требуется свежая WebAuthn-подпись существующим ключом owner с обязательной проверкой пользователя (UV), RP ID, Origin и одноразового challenge. Проверка, потребление challenge, обновление counter и выпуск разрешения теперь атомарны.
- Разрешение хранится только на сервере, действует две минуты, привязано к сессии, действию и **конкретному активному ключу**, прошедшему проверку. Старые разрешения без этой привязки отвергаются. Отозванный proof-key не позволяет использовать оставшийся grant.
- Резервная регистрация привязывает новый credential к тому же owner; создание новой owner-учётной записи не производится. Повторная регистрация не заменяет существующий или отозванный credential.
- Кнопка «Проверить этот ключ» запрашивает именно выбранный credential. Проверка сама по себе **не разрешает добавлять или отзывать ключи**. Статус `backupVerified` требует двух активных credentials с подтверждённым использованием; это не доказательство нахождения на разных физических устройствах.
- Отзыв требует свежего подтверждения **другим, остающимся ключом**. Последний ключ защищён. Отзыв, аудит и удаление всех серверных сессий owner выполняются атомарно. Все старые owner cookies и grants перестают работать; затем нужно заново войти по QR с оставшимся ключом.
- Защищённые операции с серверной сессией сериализуются с отзывом и при сохранённом парольном fallback. Общий legacy password cookie остаётся отдельно действующим: он не имеет персонального отзыва.

WebAuthn подтверждает user verification; нельзя принудительно требовать именно Face ID вместо Touch ID/кода устройства. Резервный аппаратный ключ рекомендуется хранить отдельно от основного iPhone. Синхронизированные credentials могут иметь общий источник отказа.

## Миграции и проверка Neon

Порядок SQL:

1. `db/admin-passkey-schema.sql`
2. `db/admin-roles-schema.sql`
3. `db/admin-employee-invites-schema.sql`
4. `db/admin-owner-step-up-schema.sql`
5. `db/admin-owner-step-up-proof-schema.sql`

Последняя миграция добавляет nullable FK `verified_credential_id` к таблице grants. Не изменяет существующие credentials или таблицы магазина; старые grants не получают выдуманное доказательство. Используются ограниченные lock/statement timeouts. Код production owner-mode нельзя включать до применения всех пяти миграций.

Скрипт `node scripts/admin-schema-preflight.mjs` использует `SKP_SCHEMA_DATABASE_URL`, заданный через защищённое окружение, желательно с ролью только для чтения. **Не передавайте пароль/URL в чат, аргументы команд или логи.** Скрипт открывает `REPEATABLE READ READ ONLY`, читает metadata из information_schema/pg_catalog, показывает недостающие таблицы/добавляемые поля, конфликтующие типы/PK и constraints для ревью. Он не выполняет SQL миграций и не читает содержимое заказов. Совпадение колонок не заменяет ревью constraints, индексов, прав, backup и возможности отката.

В этой сессии production connection отсутствует: **фактическая схема Neon не проверена**. Миграции проверяются в одноразовой CI PostgreSQL 16: повторное применение, сохранность существующего каталога, обнаружение отсутствующей добавляемой колонки и несовместимого типа. Это проверка SQL-совместимости с PostgreSQL, не свидетельство соответствия конкретной Neon-базы.

## Проверки

- CI исходного `05f5b30` и фактического входного `154b0a7` успешен.
- Автотест production-mode моделирует реальную ES256-подпись и `fmt:none` attestation: первичный owner → свежий step-up → регистрация backup → отдельная проверка backup → отзыв первичного с доказательством оставшегося ключа → инвалидирование всех owner-сессий.
- Отрицательные сценарии: выключенный флаг, staging/preview runtime, чужой Origin, неправильная подпись/UV, другая browser-сессия, replay, отзыв proof-key, конкурирующий отзыв, удаление последнего ключа, legacy password попытка управления owner.
- Тесты grant scope/expiry/rollback/concurrency и всего QR-входа сохраняются. TypeScript и production-like Vercel build выполняются в GitHub Actions без deploy и production secrets.
- Камера, установка PWA и системный Face ID на физическом iPhone требуют участия владельца после отдельно разрешённого deployment; синтетический authenticator этого не заменяет.

## Последовательность внедрения и откат — только после подтверждения

1. Предоставить доступ только для чтения к схеме Neon либо выполнить preflight и передать обезличенный отчёт. Проверить фактические constraints/индексы/права и migration drift.
2. Зафиксировать текущий рабочий Vercel deployment ID и SHA, сохранить настройки окружения безопасно, подтвердить восстановимый backup Neon. **Код rollback не восстанавливает данные БД.**
3. Получить отдельное разрешение на аддитивные миграции. Применить пять SQL в согласованном порядке, проверить магазин и парольный вход. Не делать DROP при обычном откате.
4. Получить отдельное разрешение на merge и deployment точного зелёного SHA. На первом запуске owner-backup flag выключен; `SKP_ADMIN_REQUIRE_PASSKEY` остаётся unset/false, `ADMIN_PASSWORD` не меняется. Сначала проверить каталог, заказы, отзывы, media и пароль.
5. Если owner ещё отсутствует, только после отдельного разрешения выполнить ручной bootstrap с коротким приглашением. При существующем owner повторный bootstrap запрещён. Войти через его Passkey, затем отдельно разрешить production owner-backup flag.
6. На основном домене выполнить iPhone + компьютер сценарий, зарегистрировать второй независимый ключ, проверить **каждый**, протестировать QR-вход резервным ключом и управляемый отзыв тестового третьего ключа. Не отзывать единственный физически доступный ключ.
7. При ошибке отключить только owner-backup flag и вернуть записанный рабочий deployment; оставить новые таблицы/колонку. Парольный вход сохраняется. Отзыв ключа сам по себе не отменяется rollback кода: ключ остаётся отозванным, удалённые сессии нужно создать новым входом.

Passkey-only cutover не входит в текущую задачу. Emergency recovery при утрате всех ключей по-прежнему не реализован: общий пароль позволяет обслуживать магазин, но не должен превращаться в обход owner-идентичности. Не выполнять ручной reset owner без отдельного проверенного регламента и подтверждения.

Источники: [SimpleWebAuthn verification](https://simplewebauthn.dev/docs/packages/server), [PostgreSQL transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html).
