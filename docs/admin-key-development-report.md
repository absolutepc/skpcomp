# SKP Admin Key — отчёт разработки, 6 ноября 2026

Ветка: `feature/vercel-admin-qr-passkeys`. PR #28 остаётся Draft.
Деплой, production-миграции, включение авторизации и обращения к рабочей Neon не выполнялись.
`vercel.json` запрещает автоматический Git-деплой этой feature-ветки; остальные ветки не затронуты.

## Реализовано и исправлено

- Сканирование QR с камеры без BarcodeDetector: jsQR 1.4.0 загружается локально отдельным модулем. Кадры не покидают браузер. Обработка ограничена стороной 960 px и интервалом 150 мс; сохранены остановка камеры, отмена устаревших запусков и очистка при уходе со страницы. Проверяется origin, путь, единственный 64-символьный request; desktop secret в QR не попадает.
- QR погашается и сессия создаётся в одной PostgreSQL-транзакции. Ошибка создания сессии откатывает погашение. Конкурентно выигрывает только один компьютерный запрос с правильным секретом.
- Блокировка сотрудника, подтверждение QR, выдача сессии, выдача приглашения и привязка Passkey используют общий порядок блокировок: сначала сотрудник, затем зависимые записи. Проверка active выполняется после ожидания. Очистка после блокировки использует свежий snapshot, включая записи, созданные конкурентно до получения блокировки.
- После `SKP_ADMIN_REQUIRE_PASSKEY=true` сохранение каталога, изменение статуса заказов, чтение административных заказов/отзывов и модерация отзывов выполняются с блокировкой сотрудника и повторной проверкой сессии. Блокировка сотрудника либо предшествует операции и отклоняет её, либо ждёт её завершения. После успешного ответа на блокировку новая защищённая операция не начинается.
- При cutover также закрыты старое password-enrollment и legacy R2-upload. До cutover поведение существующего сайта сохраняется.
- Добавлены исполняемые тесты реальных QR-пикселей, WebAuthn-подписи, WebAuthn-регистрации и PostgreSQL. Исправлены устаревшие проверки магазина после ранее выполненного разделения media-provider.
- Для страниц подтверждения/приглашений и admin API заданы no-store, no-referrer и запрет встраивания во frame.
- Дизайн основного сайта, каталог и производственные данные не изменялись.

## Проверки

Локально: все 47 скриптов проверок, не требующих отдельной PostgreSQL/QR npm-зависимостей/dev-сервера; отдельно реальный локальный media-upload/readback 512 КиБ, 2 МиБ и 8 МиБ, отказ для файла больше 8 МиБ. `git diff --check` и Vercel preflight.

GitHub Actions использует Node 22, `pnpm install --frozen-lockfile`, TypeScript, сборку `pnpm build:vercel` без deploy и отдельный контейнер PostgreSQL 16. Тестовый код отказывается использовать любую БД кроме `localhost`/`127.0.0.1` с именем `skp_admin_test`; production `DATABASE_URL` не используется.

Интеграционные сценарии:

- QR normal/inverted/rotated и пустой кадр; отбрасывание чужого origin, лишних параметров и некорректного токена.
- Настоящая ES256-подпись через `@simplewebauthn/server`; отклонение неверной подписи, origin и отсутствия UV; повтор challenge запрещён.
- HTTP handlers: create → options → decision → consume → session; неправильный desktop secret, преждевременное и повторное consume отклоняются; cookie HttpOnly/Secure/SameSite=Strict.
- Регистрация по приглашению с `fmt:none` attestation, привязка credential к сотруднику, запрет повторного завершения; конкурентное погашение приглашения.
- Отказ обычному admin в staff API, запрет блокировки owner.
- Откат погашения QR при ошибке выдачи сессии.
- Пять операций, ожидающих блокировку строки сотрудника, отклоняются после её commit; существующая сессия сразу перестаёт авторизовывать.
- Привилегированная операция, начатая до блокировки, завершается перед успешной блокировкой; после неё callback не выполняется.

Первый прогон выявил конфликт преобразования UMD/ESM в Vinext. Исправлено сохранением оригинального CommonJS-дистрибутива jsQR. Полный прогон на `a18ee98` прошёл: https://github.com/absolutepc/skpcomp/actions/runs/42228077323 . Расширенный прогон на `a646f1e` (включая регистрацию по приглашению и регрессии магазина) также полностью прошёл: https://github.com/absolutepc/skpcomp/actions/runs/42228510024 .

Локальная полная установка зависимостей была недоступна из-за сетевых ошибок npm; полный TypeScript/build выполняется в CI с точным lockfile. jsQR взят из официального репозитория, с лицензией, upstream commit и SHA-256 в `vendor/jsqr-1.4.0.README.md`.

## Границы проверки и оставшиеся условия запуска

1. **Физический iPhone ещё не проверен.** Нужны Safari и установленная PWA: разрешение камеры/отказ, фон/возврат, повторный запуск, QR на экране компьютера, Face ID/Touch ID/код устройства, отмена, истёкший QR, повторное сканирование и вход компьютера. Автотест с синтетическим authenticator не доказывает работу камеры и системного Face ID.
2. **Legacy login намеренно остаётся до cutover.** Пока флаг не включён, общий пароль/legacy cookie не имеет индивидуального отзыва и не удовлетворяет модели сотрудников. Флаг не включался.
3. **Заранее выданные Vercel Blob upload tokens — внешние capabilities.** Блокировка сотрудника запрещает публикацию/сохранение каталога, но не отзывает уже выданный внешний токен загрузки. Перед запуском определить допустимый срок/квоты либо перейти к серверно-посредованной загрузке. Не обещать мгновенный отзыв такого токена.
4. **Восстановление owner и резервный Passkey** требуют отдельного проверенного регламента. Текущий bootstrap одноразовый; API приглашений ориентирован на сотрудников. Нельзя включать cutover без проверенного восстановления владельца.
5. **RP ID фиксирован:** `skpcomp.vercel.app`. Произвольные preview-домены отклоняются. Для реальных испытаний нужен согласованный отдельный HTTPS staging origin/RP с отдельной БД либо изолированная локальная тестовая среда; ослаблять origin-проверки для произвольных Host нельзя.
6. **Глобальный rate limit** ограничивает нагрузку, но один источник может исчерпать общий бюджет. Перед публичным запуском нужны отдельные ограничения на edge, очистка истёкших challenges/QR/sessions/rate-limit buckets и мониторинг. Автоматическая production-задача очистки не создавалась.
7. Приглашения — секретные bearer-ссылки на 15 минут. Доставлять лично по доверенному каналу, исключить query strings из логов/аналитики, Проверить применение заданных в `vercel.json` заголовков no-referrer/no-store/frame-ancestors на выбранном хостинге. Потерянное/утёкшее приглашение отзывать блокировкой сотрудника и создавать новую запись при необходимости.
8. Synced Passkeys могут быть доступны на нескольких устройствах; UV не означает обязательный Face ID и может быть кодом устройства. Владелец должен принять эту модель.

## Что требуется от владельца

- Согласовать отдельную staging-среду и тестовые устройства, выполнить физический сценарий с iPhone и компьютером.
- Утвердить модель восстановления owner, синхронизации Passkey и внешних upload tokens.
- После ревью миграций подготовить резервную копию и rollback; дать отдельное разрешение на production-миграции трёх SQL-файлов и bootstrap owner. Сейчас они применялись только к одноразовой CI-БД.
- Проверить owner + резервный доступ, сотрудников, блокировку и журнал событий на staging.
- Отдельно разрешить merge, deployment и затем `SKP_ADMIN_REQUIRE_PASSKEY=true`. Ни одно из этих действий не выполнено и не автоматизировано этим PR.
